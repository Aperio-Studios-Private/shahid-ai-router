## Claims verified sound (no action)

- **keyring 4.2.0 v1 API and default-store selection (P2-T02's core assumption) — CONFIRMED.** keyring 4.2.0's `[features]` are `default = ["v1"]` and `cli` only. The `v1` feature enables, per target, `windows-native-keyring-store` (Windows) and `apple-native-keyring-store/keychain` (macOS/iOS) as optional dependencies of keyring itself. `keyring::v1::Entry::new(service, user) -> Result<Entry>` then selects the platform store automatically — Windows Credential Manager on Windows, Keychain Services on macOS; no `set_default_store` call and no manual store construction required. `set_secret(&[u8])`, `get_secret() -> Vec<u8>`, `delete_credential()` exist on `v1::Entry`. Store-init failure surfaces as `NoDefaultStore` and is cached; `Entry::store_status() -> &'static Result<()>` can probe availability at startup. **Answer to the open question: yes, `Entry::new` auto-selects the platform store on both OSes, and the `v1` feature is required (default includes it).** The workspace's `keyring = { version = "4.2", features = ["v1"] }` is correct; note `features = ["v1"]` is technically redundant with `default`, harmless to keep. sair-vault's direct platform-store deps (`windows-native-keyring-store = "1.1"`, `apple-native-keyring-store = "1.0"`) are redundant-but-harmless: they unify with keyring's own optional deps (lock shows 1.1.0 / 1.0.2, matching the plan's citation).
- reqwest 0.13.5 is locked; `connector_layer` (Tower layer over the base connector) and `dns_resolver`/`dns_resolver2` (added 0.12.23, carried into 0.13) exist; custom `redirect::Policy` exists. The plan's citation is essentially accurate (see F-5 for the one version error).
- axum 0.8.9 `DefaultBodyLimit`, tower 0.5.3 `ConcurrencyLimitLayer`: exist. `Router::layer` wraps all routes **and the fallback**, so "unknown routes behind auth too" is achievable with the correct layering construct (test it — see F-2).
- SQLx 0.9 embedded `migrate!`; only schema version 0001 exists, so "test upgrades from previous schemas" (docs/07) legitimately degenerates to fresh-apply + re-apply + FK probe at this phase.
- Vault contract test plan (shared contract tests, OS tests cfg-gated, cleanup, SECURITY_RULES #2 respected) is sound. No-plaintext-fallback stance matches docs/06.
- No self-waiving of gates in the plan; macOS claim discipline matches ADR-013 on its face (but see F-8).

## Findings

### F-1 — High — Gateway middleware — ADR-011 stack incomplete: per-request timeout budget missing; ConcurrencyLimit behavior at capacity undecided
**Description:** ADR-011 commits the stack as "token auth → Host allowlist → body size limit → concurrency limit → **timeout budget**". The plan's P2-T03 design lists only auth, Host allowlist, `DefaultBodyLimit`, `ConcurrencyLimitLayer` — the timeout budget is dropped.
**Why it matters:** tower's `ConcurrencyLimitLayer` applies *backpressure* (waits in `poll_ready`), it does not reject. Without a per-request timeout, a malicious local client (an in-scope threat per docs/06: "malicious local clients") can open loopback connections and drip bytes slowly, holding all concurrency slots indefinitely and starving the gateway — a trivial local DoS. It also interacts badly with FR-017 drain (drain waits on hung requests until the grace period expires, every time).
**Evidence:** DECISION_LOG.md ADR-011 vs phase2-plan.md §Gateway token & middleware; tower 0.5 `ConcurrencyLimitLayer` semantics.
**Resolution:** Add the timeout layer (e.g. `TimeoutLayer` with per-route budget from config) to the stack between concurrency limit and handlers, and decide + document behavior at capacity (small bounded queue vs. immediate 503/429). Negative tests: slow-headers client is dropped within budget; slot exhaustion yields a bounded, observable rejection rather than unbounded queueing. Unbounded waits are the default if this is left implicit — do not leave it implicit.

### F-2 — Medium — Gateway middleware — /healthz auth status undefined; Host-allowlist edge cases unspecified
**Description:** The current skeleton (`crates/sair-gateway/src/lib.rs:29-31`) serves `/healthz` with no auth. The plan says "unknown routes behind auth too" but never states whether `/healthz` is exempted. Whatever the implementer inherits becomes the decision. Additionally the Host allowlist is specified only by its positive list; the rejection edge cases are unspecified: missing `Host` (HTTP/1.0), absolute-form request targets, non-exact matches (`127.0.0.1.evil.com`, `evil.com/127.0.0.1`-style suffix/prefix games), case normalization (`LOCALHOST`), and the `[::1]` entry — which is unreachable if the gateway binds `127.0.0.1` only (FR-005 says loopback bind by default; dual-stack loopback vs. 127.0.0.1-only is an undecided config fact that changes the allowlist).
**Evidence:** `crates/sair-gateway/src/lib.rs`; planning-audit R-5; plan §Gateway.
**Resolution:** State explicitly: `/healthz` either sits behind auth (recommended — it discloses service presence and keeps the invariant "no unauthenticated route exists", trivially testable) or is exempted with a one-line justification recorded against R-5. Require exact host match with optional port, case-insensitive, reject missing Host with 403, and decide bind address(es) (drop `[::1]` from the allowlist if binding v4-only). Negative tests: spoofed-suffix Host, missing Host, HEAD on protected route (axum `get` also serves HEAD — assert middleware runs), chunked oversized body rejected by `DefaultBodyLimit`, and a fallback-route (404) request asserting the auth layer wraps the fallback.

### F-3 — High — SSRF — "connect to validated IP directly" conflicts with reqwest's TLS identity model; scheme policy and denylist extensions missing from SsrfPolicy
**Description:** The plan specifies a custom connector (`tower::Service<Uri>`): resolve → validate every address → connect to the validated IP directly. reqwest 0.13 offers no full connector replacement — only `connector_layer` wrapping the base connector. The workable reading (validate, then rewrite the target to the IP literal and hand it to the inner connector) has a fatal TLS consequence: the upstream TLS layer derives SNI and certificate identity from the (rewritten) host, so verification runs against the IP literal — https upstreams fail verification, and the only way to "fix" that is weakening verification, which SECURITY_RULES #6 forbids.
**The sound mechanism on reqwest is a validating custom resolver:** implement `Resolve` (`dns_resolver`/`dns_resolver2`) so resolution and validation happen together and only validated `SocketAddr`s are returned; reqwest connects exactly to the resolver's addresses (no re-resolution between validate and connect — the TOCTOU window R-6 demanded closed is closed), while SNI and certificate verification remain bound to the original hostname. `redirect::Policy::custom` gives per-hop checks, and each hop re-triggers the validating resolver.
Also missing from `SsrfPolicy` despite docs/06 explicitly mandating them: **scheme enforcement** (HTTPS by default; `http` only for explicit loopback literals; reject non-HTTP schemes) and CRLF/header-injection rejection at the adapter boundary. Denylist should extend beyond R-6 with: multicast `224.0.0.0/4`, reserved `240.0.0.0/4`, IPv6 transition prefixes `64:ff9b::/96` (NAT64) and `2002::/16` (6to4), and a default-deny posture for any address family/range not explicitly classified public.
**Evidence:** docs.rs reqwest 0.13.5 `ClientBuilder` (no replacement-connector API; `connector_layer` bounds; `dns_resolver`); docs/06 "HTTPS by default… Reject CRLF/header injection and non-HTTP schemes"; planning-audit R-6; plan §SSRF connect layer.
**Resolution:** Amend P2-T05: enforcing mechanism = validating resolver + `redirect::Policy::custom` (keep `connector_layer` only if a documented experiment proves original-hostname TLS identity survives — otherwise do not use it); add scheme policy to `SsrfPolicy` now (the layer is built this phase even though custom-URL CRUD lands in Phase 3); extend the denylist as above with each range unit-tested, plus a default-deny test (unclassified address type → blocked). Test strategy gap: literal-IP tests never exercise the resolve path — require an injectable/mock `Resolve` so hostname→mixed-address (rebinding-shaped) scenarios are tested offline, asserting only validated addresses ever reach the connect call.

### F-4 — Medium — Vault/schema — planned secret-ref format contradicts the existing `SecretRef` validator
**Description:** The plan stores refs "like `sair://cred:<uuid>`", but `SecretRef::parse` (`crates/sair-vault/src/store.rs:19-29`) accepts only `[A-Za-z0-9._-]` — `:` and `/` are rejected, so every planned ref fails validation on first use. The account names (`cred:<uuid>`, `gateway-token`) are fine for the OS store; only the DB-side ref format is contradictory.
**Evidence:** phase2-plan.md §Vault implementation; `crates/sair-vault/src/store.rs`.
**Resolution:** Pick one before P2-T02: (a) extend `SecretRef` to parse a bounded scheme (`sair://` prefix, then the same restricted charset for the remainder, ≤256 total) with unit tests, or (b) use a charset-safe format (`sair.cred.<uuid>`, `sair.gateway-token`). Pin the exact format in a unit test so vault and persistence cannot drift.

### F-5 — Medium — Research integrity — "ring 0.23" is a nonexistent version; repo locks ring 0.17.14
**Description:** The plan's "Verified facts" state "ring 0.23 `SystemRandom`…". docs.rs lists no ring 0.23 (latest 0.17.14, matching `Cargo.lock`, pulled via rustls 0.23). The cited APIs (`SystemRandom`, `constant_time::verify_slices_are_equal`) exist in 0.17, so the design stands — but this plan's predecessor review (R-4) was precisely about wrong version/feature facts, and ADR-006's value is version-precise crypto decisions. A false "verified fact" in the same section that gets keyring right erodes the section's audit value.
**Evidence:** `Cargo.lock` (ring 0.17.14); docs.rs/ring (no 0.23).
**Resolution:** Correct the fact; add `ring = "0.17"` as a direct workspace dependency (same version line rustls uses — do not introduce a second ring major); note the fixed-length property (43-char base64url of 32 bytes) for the comparison flow.

### F-6 — Medium — Schema — `request_records` omits the selected deployment/credential (FR-011); delete rules and `schema_migrations` left implicit
**Description:** FR-011 requires history to record "status, latency, **selected deployment** and token usage". The plan's `request_records` list (correlation_id, status, latency, token counts, error_category) omits the selection. Also unspecified: FK delete rules for the docs/05 flows — `credentials.provider_id` (CASCADE), `credentials.account_id → provider_accounts` (SET NULL; account-level quota truth per docs/05 "quota truth" requires the nullable account link to survive), `alias_deployments` (CASCADE both sides; a deployment deletion may leave an alias empty — that state must be surfaced per FR-012, not silently RESTRICTed), `health_events.credential_id` (SET NULL vs CASCADE — pick and test), and history survival semantics for request_records (recommend denormalized provider/model/deployment labels + nullable `SET NULL` FK, so retention and deletions never RESTRICT). docs/07's `schema_migrations` entity is satisfied by sqlx's `_sqlx_migrations` — state that explicitly so the entity list isn't judged incomplete.
**Evidence:** docs/01 FR-011; docs/05 §Quota truth/§Retry safety; docs/07 entity list; phase2-plan.md §Schema.
**Resolution:** Amend the schema section: add selected-deployment reference (nullable FK ON DELETE SET NULL) + denormalized labels to `request_records`; enumerate every FK with its delete rule and add an FK-probe test per rule (the current "FK enforcement probe" is one test for many rules). Add the remaining hot-path indexes now (alias_deployments by alias_id, deployments by model_id, health_events by credential_id+ts) or state why two indexes suffice for v1.

### F-7 — Medium — FR-020 — retention delete query is tested but the automatic cleanup is not designed
**Description:** FR-020 (via G-04 amendment) is "retention default 30 days with **automatic cleanup on startup and daily**". The plan tests only the delete query; no design or task covers the scheduler (startup pass before gateway bind + daily interval), the configurable window in `app_settings`, or a floor on the configured value.
**Evidence:** docs/01 FR-020; planning-audit §2 G-04; phase2-plan.md §Schema tests / §Tasks.
**Resolution:** Either design it into P2-T01/T03 (tokio interval task owned by app state; startup purge before bind; configurable days with a sane minimum) or explicitly mark FR-020 partial in this phase's traceability with the deferral recorded — currently it will read as covered while only the SQL exists.

### F-8 — Medium — macOS evidence — test gating contradicts the CI reality; Keychain-in-CI outcome undecided
**Description:** The plan gates OS vault tests `#[cfg(any(windows, target_os = "macos"))]` and simultaneously assumes "macOS vault behavior compiles under CI; runtime verification is the owner's". Those two cannot both hold: CI runs `cargo test` on macos-latest (P1-T05, ADR-013), where cfg-gated macOS tests **will execute** — that is runtime verification, contradicting the plan's own evidence discipline. Worse, macOS Keychain access from unsigned test binaries is known to fail environmentally (`errSecMissingEntitlement` / -34018 in some runner configurations), which would turn the first CI run red or tempt someone to silently `#[ignore]` the tests — both corrupt phase evidence.
**Evidence:** phase2-plan.md §Assumptions; tasks/BACKLOG.md P1-T05; DECISION_LOG.md ADR-013; docs/12 platform-evidence pipeline.
**Resolution:** Decide and document before P2-T02: (a) macOS vault tests run in CI and green CI constitutes the macOS evidence per ADR-013 (preferred — it *is* runtime evidence), with a pre-agreed, documented fallback (annotation + skip reason recorded in the report, not silent) if entitlement errors appear; or (b) explicitly `#[ignore]` on CI macOS until the owner's 2026-11-01 verification, with the ignore reason in code. Either way, reports must state exactly which platform executed the vault contract tests (QUALITY_GATES: state what was tested).

### F-9 — Medium — Lifecycle — FR-017/FR-018 have no explicit tests; drain-on-app-exit caller unnamed; start must fail closed on token retrieval failure
**Description:** The plan builds `GatewayHandle::start/stop(grace)` but lists no test for the drain behavior (FR-017: in-flight requests complete within the bounded grace period) or for bind failure surfacing (FR-018: explicit error, no fallback port). It also never names who invokes `stop` on **app exit** (vs. manual UI stop) — in Tauri that is the `RunEvent::ExitRequested`/exit hook in the `tauri::Builder` run loop; if unnamed, FR-017 likely gets wired only to the manual stop path. Finally: the plan's degraded-start covers vault-unavailable-at-app-startup, but not vault-failure-at-gateway-start — the gateway must refuse to start without a retrieved token (fail closed), surfacing the error state.
**Evidence:** phase2-plan.md §Gateway token & middleware, §Security/privacy risks; docs/01 FR-017/FR-018/FR-022; docs/02 §Failure isolation ("Migration failures must stop safely" — the plan covers this; extend the same treatment to the token path).
**Resolution:** Add to P2-T03's acceptance: (1) integration test — slow in-flight request completes (or is aborted cleanly) when `stop(grace)` fires; graceful shutdown via axum's shutdown-future so streaming-ready wiring exists before Phase 7; (2) integration test — bind to an occupied port returns `GatewayError::Bind` and the state surfaced to UI is the explicit error, with an assertion that no fallback bind is attempted; (3) name the Tauri exit hook that triggers drain; (4) assert start fails closed when the vault token read fails (no tokenless gateway).

### F-10 — Low — Token lifecycle — regeneration ordering, mock-store release guard, and reveal-path sweep
**Description:** Three small hardening details in P2-T03: (1) `regenerate_gateway_token` ordering is unspecified — overwrite-in-place on the same account `gateway-token` means a crash between `set_secret` and the `app_settings` ref update leaves DB and vault disagreeing (auth bricked until another regeneration). (2) The plan claims the mock store is "enforced by app crate not enabling the feature + a unit assertion" — a runtime unit assertion cannot enforce a build configuration; use a compile-time guard (e.g. `#[cfg(all(feature = "mock", not(debug_assertions))] compile_error!(...))` in sair-vault) so a release build with `mock` enabled fails to compile. (3) The redaction sweep (P2-T04) covers the middleware stack but should also cover the vault roundtrip and the reveal command's logging path, since those are the other places the token exists in memory.
**Evidence:** phase2-plan.md §Vault implementation, §Gateway, §Redaction; `crates/sair-vault/src/store.rs:80-126` (mock currently compiled unconditionally — the feature gate itself is Phase 2 work).
**Resolution:** Regenerate = write NEW vault item under a fresh uuid account → swap the `app_settings` ref → delete the old item. Add the compile-time guard. Extend the sweep matrix to vault + reveal paths. Constant-time comparison via `verify_slices_are_equal` is fine; check length first (fixed 43 chars) then compare, and document that a length-mismatch early-out leaks only length, which is public.

### F-11 — Low — Redaction — log file location, permissions, rotation unspecified; field-name layer is acceptable as depth-in-depth
**Description:** P2-T04 sends tracing to stderr + file but never says where the file lives or how it is bounded. Put it under the OS per-user app-data dir (Tauri path resolver: `%APPDATA%/<app>/logs`, `~/Library/Logs`) so ACLs inherit user-only on both platforms; cap size and rotate (unbounded plaintext logs on disk are their own leak vector and interact with FR-016 export later). The field-name rewrite layer is fine as defense-in-depth given the primary rule (values never enter spans) — note its obvious limit (message-text leakage is not caught by field rewriting; the sweep tests are the guard there).
**Evidence:** phase2-plan.md §Redaction; docs/06 §Privacy; ADR-008.
**Resolution:** Specify log dir, rotation/size cap, and that no request/response bodies are ever written (ADR-008) in the P2-T04 task text; add one test asserting the file writer path (not just the `MakeWriter` in-memory path) contains no seeded key material.

### F-12 — Low — QUALITY_GATES mapping — dependency audit and threat-model update absent from the phase gate
**Description:** QUALITY_GATES requires, for security-sensitive changes: threat-model update, negative tests, secret inspection, **dependency/permission review**, and independent security review. The plan's phase gate includes the security review and tests but omits the dependency audit (`cargo audit`/`cargo deny` — keyring, ring, and platform-store crates enter the tree this phase) and any threat-model update (docs/06 threat model should gain: local log files, token-reveal IPC command, degraded-start states).
**Evidence:** `.agent/QUALITY_GATES.md`; phase2-plan.md §Acceptance criteria.
**Resolution:** Add `cargo audit`/`cargo deny` to the P2-T06 gate and a short threat-model addendum to docs/06 (or an audit note referencing it) as part of P2-T06.

## Verdict

The plan's architecture is coherent and its keyring v1 claims — the highest-risk external dependency — are confirmed against docs.rs, including automatic platform-store selection on Windows/macOS under the `v1` feature. The findings are concentrated in completeness of committed behavior (timeout layer, FR-017/018 tests, FR-020 cleanup) and one implementation-mechanism correction with security consequences (F-3). None invalidate the phase structure or task order.

**VERDICT: APPROVE WITH CHANGES**

Resolve before or during implementation, as gates:
- **F-1, F-3 (High):** must be incorporated into the plan text (P2-T03 / P2-T05) before those tasks start — F-3 changes the SSRF mechanism; F-1 adds a committed ADR-011 layer.
- **F-4, F-6, F-8, F-9 (Medium):** incorporate in the corresponding tasks; F-8 needs a decision before the first CI run of this phase.
- **F-2, F-5, F-7, F-10, F-11, F-12:** fold into task acceptance criteria; no structural impact.
