## Verified positives (checked, no finding)

- **generateContent is not replaced.** Google's Interactions API (recommended for new projects, SDK 2.3.0+) is a complementary surface; v1beta `models/{model}:generateContent` remains fully supported (labeled "legacy", not deprecated). ADR-010 stands; the plan's surface choice is correct. Recommendation only: record this verification in the ADR-010 revisit-trigger trail so Phase 8 does not re-litigate.
- **The plan's Gemini error-shape basis is correct for the target surface.** v1beta generateContent still returns google.rpc-shaped errors `{error:{code:<int>,message,status:"RESOURCE_EXHAUSTED",...}}` (confirmed by 2026 sources: gemini-cli issues, Vertex threads, Sept-2026 troubleshooting guides). The new snake_case shape (`rate_limit_exceeded`, `quota_exceeded`, …) documented on the current ai.google.dev api-errors page belongs to the Interactions API — a different surface. No impact; worth one sentence in the plan to prevent future confusion.
- **Wire facts check out:** `POST {base}/v1/messages` with `x-api-key` + `anthropic-version` + `content-type`; error shape `{type:"error",error:{type,message},request_id}` with the listed type names; `POST /v1/messages/count_tokens`; Gemini `POST {base}/v1beta/models/{model}:generateContent` with `x-goog-api-key`; `usageMetadata.promptTokenCount`/`candidatesTokenCount` (plus `totalTokenCount`/`thoughtsTokenCount`/`cachedContentTokenCount`).
- **`?key=` can never authenticate.** `token_auth`/`extract_token` (crates/sair-gateway/src/lib.rs:195-233) reads only `Authorization: Bearer`, `x-api-key`, `x-goog-api-key` headers; query parameters are never consulted. Rejecting `?key=` is defense-in-depth, fail-closed either way, and consistent with SECURITY_RULES #8 (Google does support `?key=`, but the header is the documented approach).
- **Same-protocol routing is already enforced where the plan claims:** `plan_route` filters on `supports_protocol(family)` first (routing.rs:100) and `load_route_snapshot_detailed` parses the model row's `protocol_family`; an openai-only alias on `/v1/messages` correctly yields NoEligibleDeployment with `protocol_mismatch` reasons.
- **Records are safe for the new families:** `request_records.protocol_family`/`operation` are free TEXT (0001_init.sql:129-147 — no CHECK), so `anthropic_messages`/`gemini_generate_content` values need no migration; `models.protocol_family` and `agent_profiles.protocol_family` CHECKs already include the new values.
- **Axum 0.8 routing works as planned:** `{model_and_method}` captures the full segment; a colon inside a request path segment is not special in matchit 0.8. The v0.7-compat construction panic (#484) triggers only when a route DEFINITION segment starts with `:` — the plan's `{param}` form is unaffected — and capturing the whole segment (rather than a literal `…:generateContent` static suffix route) avoids the literal-colon problem of #2128 entirely.
- Adapter pattern replication (`classify` body-aware, status-first, ContextLimit-before-InvalidRequest, header + body Retry-After with 3600s cap, `MAX_RESPONSE_BYTES` bound, malformed-200 never passthrough) matches ADR-017 and the existing openai.rs contract; SSRF/vault-at-call-time/per-deployment semaphore flow is shared by construction per ADR-015's Phase 3 rule.

## Findings

### F-1 — High — Per-family HTTP status mapping is undefined; reusing `upstream_failure_response` collapses upstream statuses to 502
- Category: Protocol fidelity (FR-006) / plan completeness.
- Evidence: Plan §1 defines per-family error ENVELOPES and §2 says "Upstream status + error type preserved", but the only status mapping in the codebase is `upstream_failure_response` (crates/sair-gateway/src/api.rs:126-147): `RateLimited→429`, `Timeout→504`, everything else→`502`. If the new surfaces reuse it, an upstream Anthropic `400 invalid_request_error` (e.g. missing `max_tokens`), `413 request_too_large`, or `529 overloaded_error` surfaces as HTTP 502 wearing an anthropic error type; same for a Gemini `400 INVALID_ARGUMENT`. Anthropic and Gemini SDKs dispatch on status code first — a 502 with `error.type="invalid_request_error"` is semantically incoherent to them, and the semantics loss is exactly what FR-006's passthrough surfaces exist to prevent. (The OpenAI surface's 502-collapse is existing, test-guarded behavior — out of scope here.)
- Consequence if implemented as written: the implementer inherits the shared helper and the new surfaces are status-lossy from day one, with the plan text asserting the opposite.
- Recommendation: add a per-family status rule to the plan: when the failure carries an upstream status from a same-protocol upstream (same protocol, different provider), preserve it verbatim (`failure.status`); fall back to the category→status defaults only for gateway-local failures and transport failures (no status). Pin with tests: upstream 400→400, 413→413, 429(+Retry-After)→429, 529→529, `UNAVAILABLE` 503→503 — each asserted in the family envelope.

### F-2 — High — Upstream timeout error types are missing from the classification matrices; the new surfaces would rotate on ambiguous timeouts
- Category: Failover safety (docs/05 "Duplicate execution", ADR-017) / correctness.
- Evidence: The plan's Anthropic list has no `timeout_error` (HTTP 504, verified on the errors reference) and the Gemini list has no `DEADLINE_EXCEEDED` (504). Both fall into the plans' `5xx→ProviderUnavailable` buckets, whose rotation action is `Rotate` (crates/sair-domain/src/error.rs:75-90), while `Timeout→Stop` exists precisely because "generation may have executed upstream" (ADR-017(1), docs/05). A model that times out upstream would silently trigger a second billed generation on another credential.
- Recommendation: map `timeout_error`→`Timeout` and `DEADLINE_EXCEEDED`→`Timeout` before the 5xx fallbacks; add rotation-behavior tests mirroring openai.rs `quota_429_stops_rotation_but_rate_limit_rotates` (assert `FailureAction::Stop` for both), per docs/11's mandatory "ambiguous timeout" scenario.

### F-3 — Medium — Both direction maps are incomplete: classification catch-alls and envelope-side name tables are unspecified
- Category: Envelope fidelity / completeness.
- Evidence: (a) Classification (wire→category): no stated default for Anthropic types not listed — notably `conflict_error` (409, verified) and any future type — nor for Gemini statuses beyond the listed ones (`ABORTED`, `ALREADY_EXISTS`, `CANCELLED`, `UNIMPLEMENTED`, `UNKNOWN`). The openai.rs `classify` pattern (openai.rs:229-253) survives this via the status-based fallback; the plan must say the new classifiers keep it (status-first, type/status only as modifiers). Anthropic now also has a first-class `billing_error` (402) type (verified) — the plan's fuzzy "billing/credit hints" rule should anchor on it explicitly. (b) Envelope (category→wire name): the plan says `error.type`/`status` use provider names and gives two examples, but our `ErrorCategory` has 11 variants; unspecified: `ContextLimit` (→`invalid_request_error`? →`INVALID_ARGUMENT`?), `ModelUnavailable` (→`not_found_error`/`NOT_FOUND`?), `TransportFailure` (→`api_error`/`UNAVAILABLE`?), `Unknown`. A missing table means the implementer improvises per call site.
- Recommendation: add two tables to the plan — classify (wire name/status → category, with the status fallback as default) and envelope (every ErrorCategory variant → anthropic error type; every variant → Gemini status) — and a unit test asserting exhaustiveness over the enum.

### F-4 — Medium — Gateway-local errors have no wire-legal names in the new envelopes
- Category: Envelope fidelity / ADR-010 compliance.
- Evidence: Every pre-upstream rejection on the new surfaces (`invalid_json`, `model_required`, `alias_not_found`, `streaming_not_supported`, `deployment_busy`, `no_attempt_made`, storage failures — api.rs:157-531) currently emits an OpenAI-style `code`. On the Anthropic surface the plan requires Anthropic's type names, but gateway-local errors have no upstream origin; worse, the count_tokens 501 (ADR-010 "structured 501 otherwise") has no Anthropic-native error type at all (Anthropic's status/type table has no 501; verified). The plan is silent on all of these.
- Recommendation: specify, per family: 400-class gateway-local errors emit `invalid_request_error` / `INVALID_ARGUMENT` with the machine code in `shahid` (as the plan already does for categories); the count_tokens 501 emits an explicitly documented type (e.g. `invalid_request_error` with `shahid.code="count_tokens_not_supported"` and HTTP 501, or a namespaced gateway type — decide and test the exact shape).

### F-5 — Medium — `anthropic-version: 2023-06-01` is no longer the current pin; forwarding policy undecided
- Category: Factual staleness / protocol fidelity.
- Evidence: Re-verified 2026-10-31 (platform.claude.com versioning + corroborating sources): Anthropic released `2026-10-21` — the first new version since 2023 — as the SDK 2.0 default; `2023-06-01` remains fully supported (legacy), and `2026-10-21` removes sampling parameters (`temperature` etc. now return 400). The plan hard-pins `2023-06-01` calling it "verified docs 2026-10-30/31" without discussing the new version. Consequences: SDK 2.0 clients (which send `anthropic-version: 2026-10-21`) get silently downgraded to 2023-06-01 upstream semantics; conversely, pinning the new version would break clients that send `temperature`.
- Recommendation: for a passthrough gateway, forward the client's `anthropic-version` header when present (validated through the existing `is_header_safe` helper — it is client-controlled input per SECURITY_RULES #7) and use a pinned default (decide: `2023-06-01` for temperature compatibility, documenting why) when absent. At minimum, record the decision and correct the plan's verification claim.

### F-6 — Medium — Per-family validation and capability derivation are named but not specified
- Category: Family-parameterization completeness / FR-007.
- Evidence: Plan §1 lists "request validation" as a per-family dimension but specifies nothing. (a) Verified Anthropic required fields are `model`, `messages`, `max_tokens`; a client body missing `max_tokens` currently reaches the upstream, gets a 400 `invalid_request_error`, is classified InvalidRequest, records an upstream attempt, writes a `degraded` health event for a healthy credential — and (with F-1 unfixed) surfaces as 502, not 400. The challenge's expectation (gateway-side 400 in the anthropic envelope) is the right behavior; the plan must say so for `max_tokens`/`messages` (and the Gemini surface's `contents`). (b) `CapabilityRequirements::derive_from_body` (crates/sair-domain/src/routing.rs:66-83) is OpenAI-shaped: `tools` non-empty works for all three families, but `response_format` doesn't exist in Anthropic, and Gemini's structured-output signals (`generationConfig.responseMimeType:"application/json"`, `responseSchema`) are not detected — the Gemini surface silently under-filters on `structured_output`.
- Recommendation: enumerate per-family validation (what is checked gateway-side, in which envelope it 400s) and extend `derive_from_body` per family (or record the Gemini structured-output under-filter as an explicit deferral, Phase-5-F-2 style).

### F-7 — Medium — Gemini quota discrimination and retryDelay parsing will misroute free-tier quota exhaustion
- Category: Rotation safety (docs/05 "Quota truth") / classification fidelity.
- Evidence: (a) On the Gemini API (unlike Vertex), 429 `RESOURCE_EXHAUSTED` responses typically carry no `details[].@type=QuotaFailure`; the body is `{"code":429,"status":"RESOURCE_EXHAUSTED","message":"Resource has been exhausted (e.g. check quota)."}` or "You have exhausted your capacity on this model" (2026 sources). The plan's rule ("BillingOrQuota when details/status hints contain QuotaFailure/billing, else RateLimited") therefore defaults most real quota exhaustion to RateLimited→rotate, burning sibling keys of the same Google project — the exact failure mode docs/05 forbids. (b) Gemini signals retry timing via `details[].@type=google.rpc.RetryInfo` `retryDelay` ("12.3s"), not a Retry-After header; the plan doesn't parse it, so `cooldown_for` falls back to policy cooldown and loses provider-advised timing.
- Recommendation: (a) add message hints ("exhaust", "quota") → BillingOrQuota alongside the details check, with both branches tested (the plan's "RESOURCE_EXHAUSTED both ways" test must then use realistic bodies); (b) parse `retryDelay` (seconds format, capped at 3600 like the header path) into `retry_after_secs`.

### F-8 — Low — count_tokens semantics under-specified (and the challenge's alias-resolution worry is unfounded)
- Category: Spec gap.
- Evidence: Verified: the count_tokens request body REQUIRES `model` and `messages` (response: `{"input_tokens": N}`), so alias resolution works identically to `/v1/messages` — the plan's proxying design is sound. Unspecified: rewriting `model` inside the count_tokens body, mapping `input_tokens`→`tokens_in` (and tokens_out=None) in records, `operation="count_tokens"` in request records, and §3's internal contradiction ("single attempt per candidate … but keep the same bounded loop for consistency").
- Recommendation: one paragraph: same model-rewrite as messages; record with `operation="count_tokens"`, `tokens_in=input_tokens`; pick "same bounded loop" (rotation on RateLimited/ProviderUnavailable is safe here — counting is idempotent) and delete the contradictory sentence.

### F-9 — Low — `?key=` rejection test must account for middleware ordering and envelope
- Category: Test adequacy.
- Evidence: Confirmed the auth middleware reads headers only, so `?key=` alone is rejected by `token_auth` with the generic `{error:{code:"unauthorized"}}` body and never reaches the handler. The plan's `query_param_auth_rejected` response is therefore only reachable with a VALID gateway header plus `?key=` — the plan doesn't say which path the test exercises, nor which envelope the handler's 401 uses.
- Recommendation: two tests: (1) `?key=` without any header → 401 at middleware (generic body, proves no query-param auth); (2) valid header + `?key=` → 401 in the Gemini envelope with `shahid.code="query_param_auth_rejected"`.

### F-10 — Low — Percent-encoded colon in the Gemini path segment
- Category: Routing robustness.
- Evidence: The `{model_and_method}` capture matches regardless of encoding, but axum percent-decodes in the `Path` extractor while the raw URI retains `%3A`. If the handler parses the `:generateContent` suffix from the raw URI instead of the decoded extractor, a legitimately percent-encoded client request 404s.
- Recommendation: parse the suffix from the decoded `Path<String>` value; add an encoded-colon request to the surface tests; keep "unknown suffix → 404" (it correctly stays behind auth like every route).

### F-11 — Low — Gate/test-plan gaps vs QUALITY_GATES and docs/11
- Category: Gate compliance.
- Evidence: (a) QUALITY_GATES "Provider" gate includes "opt-in live test"; the plan is mock-only and does not state live-test status — the same honesty gap Phase 5 review flagged (F-7 there). (b) Missing from the test list: capability-mismatch on a new family (docs/11 mandatory "capability mismatch"); malformed-200 rejection for the Gemini adapter (listed only for Anthropic; ADR-017 requires "never passthrough" for both); timeout classification/rotation tests (F-2); `/v1/messages` against an openai-only alias asserting the NoEligibleDeployment 503 renders in the ANTHROPIC envelope (only the count_tokens 501 variant is listed); Gemini `retryDelay`→cooldown (F-7).
- Recommendation: add the stated live-test status line ("opt-in live Anthropic/Gemini tests deferred; all Phase 6 evidence mock-based") and the listed tests.

## Verdict

VERDICT: APPROVED WITH REQUIRED REVISIONS — F-1 and F-2 must be incorporated into the plan before implementation begins (status fidelity on the new surfaces and timeout-rotation safety are the two places where implementing as written produces behavior that contradicts the plan's own text and ADR-017/docs/05); F-3–F-7 should be folded into the same plan revision; F-8–F-11 are recommendations. The core design is sound and externally verified: family-parameterized dispatch over the existing engine, same-protocol candidate filtering already enforced, correct wire shapes for both providers, generateContent un-deprecated, and a defensible `?key=` rejection with a fail-closed auth stack.
