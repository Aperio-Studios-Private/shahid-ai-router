## Claims verified sound (no action)

- **axum 0.8 `Body::from_stream` pattern — CONFIRMED.** Signature: `S: TryStream + Send + 'static, S::Ok: Into<Bytes>, S::Error: Into<Box<dyn Error + Sync + Send>>`. reqwest `bytes_stream()` yields `Result<Bytes, reqwest::Error>`; `TryStream` is blanket-implemented for `Stream<Item = Result<_, _>>`, `Bytes: Into<Bytes>` is trivial, and `reqwest::Error: Error + Send + Sync` satisfies the error bound. The plan's `StreamOutcome { byte_stream: Pin<Box<dyn Stream<Item = reqwest::Result<Bytes>> + Send>> }` keeps axum out of sair-providers (boundary preserved) and plugs in directly.
- **Commit-on-headers is the correct boundary.** docs/05: "After response events/bytes are committed, transparent failover is generally unsafe. Retry only before commitment." Committing at upstream-header receipt (the earliest observable point) with rotation legal only before it matches FR-010, and omitting a `commitment` flag from `UpstreamFailure` makes post-commit rotation structurally impossible — good design. Mid-stream error events (Anthropic `error` events, OpenRouter mid-stream error frames) are relayed, not rotated — correct; the plan should state this explicitly (fold into F-2).
- **Pre-commit failure semantics (challenge #5) are consistent with ADR-017**: same classification (body-aware on non-2xx), same Retry-After → cooldown + immediate rotation, same credential dedupe (R4-02), same busy-skip (R4-06), same retry budget. One bound is missing — see F-6(b).
- **FR-021 permit lifetime (challenge #2): the stream-wrapper mechanism is sound.** `OwnedSemaphorePermit` from `try_acquire_owned` (acquired before commit, critical section never spans an await, ADR-012) moved into the response body stream is released when hyper drops the body — including client disconnect — so there is no leak path and no race with the non-streaming `drop(deployment_permit)` arm. The one way to get this wrong is dropping the permit at handler return (the non-streaming habit, `api.rs:814`); the plan's "permit-carrying stream wrapper" wording must stay normative — see F-6(e).
- **Gateway 408 layer does not kill streams — verified from the locked source.** tower-http 0.6.11 `Timeout`'s `ResponseFuture::poll` returns the configured status only when the sleep fires *before* the inner future resolves; once the response head is produced the body is never wrapped (`ResponseBodyTimeoutLayer`/deadline bodies exist as separate layers, unused here). So `TimeoutLayer::with_status_code(408, timeout_ms)` bounds time-to-head only and long SSE bodies are unaffected. hyper-util `serve_connection_with_upgrades` handles HTTP/1.1 chunked responses natively; axum re-encodes the relayed stream as chunked. No server-side blocker.
- **wiremock-based tests listed in the plan are executable as written**: a buffered body with `content-type: text/event-stream` plus hit-count matchers covers frame fidelity and the "single upstream hit" no-retry assertion. Their evidentiary *limits* are the subject of F-4.

## Findings

### F-1 — High — Timeout policy — the per-attempt total deadline kills long-lived streams mid-flight (after commitment)
- **Category:** Design/timeout interplay (challenge #3, verify #3).
- **Evidence:** docs.rs reqwest 0.13.5, `RequestBuilder::timeout`: *"The timeout is applied from when the request starts connecting until the response body has finished"*; `ClientBuilder::timeout` is documented as *"a total deadline"*. This repo applies BOTH: `build_client` hard-codes `.timeout(120s)` (`crates/sair-providers/src/http.rs:244,279`) and the rotation loop adds a per-attempt request-level `.timeout(timeout)` from the policy row (`crates/sair-gateway/src/api.rs:698`; default `timeout_ms: 120_000`, `crates/sair-persistence/src/repos.rs:492`). The plan specifies *"identical request construction to non-streaming"* for the streaming variants — so any upstream stream that lives longer than `timeout_ms` (the norm for long generations) is killed mid-body **after commitment**: the client already holds a 200 head and receives a truncated stream, the record already says 200, and docs/05's ambiguous-timeout rule (surface, never blind-retry) is silently violated by design instead of addressed.
- **Recommendation:** Streaming attempts must not carry a total deadline. Build a dedicated streaming client (same `SsrfPolicy`, same `SsrfCheckedClient` wrapper — ADR-015 forbids exposing anything else) with **no** client-level `.timeout()` and rely on `connect_timeout` + `ClientBuilder::read_timeout` — docs.rs 0.13.5: read_timeout *"applies to each read operation, and resets after a successful read"*, *"more appropriate for detecting stalled connections when the size isn't known beforehand"*, i.e. idle-timeout semantics. Note both are client-level only in reqwest 0.13 (no per-request override), so `build_streaming_client(policy, connect_timeout, idle_read_timeout)` or equivalent is required; the per-request `.timeout(timeout)` call must be skipped on the streaming path. Keep ADR-017 pre-commit semantics unchanged (pre-commit timeout still classifies as `Timeout` and does not rotate); define mid-stream timeout/drop behavior explicitly: stream terminates, no rotation (structurally impossible), record keeps commit-time truth. Required tests: a stream that runs *longer than* `policy.timeout_ms` is relayed past that mark (regression guard against reintroducing the total deadline); a stalled stream (no bytes) is cut by the idle timeout.

### F-2 — High — Commit semantics — the 2xx branch of the commit predicate is incoherent as written ("2xx with a JSON error content-type" is not detectable from headers)
- **Category:** Design/commit boundary (challenge #1).
- **Evidence:** Plan §Design 1: *"2xx + SSE-ish response → StreamOutcome … Non-2xx (or 2xx with a JSON error content-type) → full body read + classify"*. Content-Type cannot distinguish an error JSON body from a success JSON body — both are `application/json`. Undefined cases the implementation will hit: (a) 200 + JSON *success* body for `stream:true` (OpenAI-compatible servers that ignore the flag exist); (b) 200 + JSON *error* envelope from proxy providers; (c) 200 + non-JSON garbage; (d) Gemini `:streamGenerateContent` without `alt=sse` returns a 200 **JSON array** (see F-3). ADR-017's rule *"malformed/oversized 200 bodies are classified errors, never passthrough"* applies to exactly this shape on the non-streaming path, so leaving the streaming 2xx branch undefined contradicts the project's own decision log. Whatever the implementer inherits becomes the decision — the same trap Phase 2 review F-2 flagged.
- **Recommendation:** Make the rule total and header-driven with one bounded-buffer exception: (1) 2xx + `content-type: text/event-stream` → commit and relay. Define "SSE-ish" as *exactly this header*, not a body sniff. (2) 2xx + any other content-type → **bounded** buffer (cap with `MAX_RESPONSE_BYTES`): parse; error envelope (`error` object / Gemini `error.status`) → classify and rotate pre-commit (rotation still legal); otherwise return the buffered body as a non-streamed success response — usage extraction still works and the record can note that the upstream downgraded the stream. Cap overflow → classified error pre-commit (the safe direction). (3) Non-2xx → bounded buffer + classify (unchanged from plan). State the boundary honestly in the plan: commitment happens on upstream *headers*, so a failure between upstream head and first relayed byte is not rotated (no resumability — docs/05), and mid-stream error events are relayed, never rotated.

### F-3 — Medium — Gemini — `alt=sse` is stripped from `:streamGenerateContent`, changing the client-visible wire format
- **Category:** Protocol fidelity (FR-006/FR-010, ADR-010).
- **Evidence:** The gateway's Gemini handler uses `RawQuery` only to reject `key=` and forwards no query (`crates/sair-gateway/src/api.rs:347-364`); the adapter builds a fixed URL with no query (`crates/sair-providers/src/gemini.rs`). Google's `:streamGenerateContent` returns a JSON array by default and SSE only with `?alt=sse`; Gemini SDKs and agents send `alt=sse`. The plan's "identical request construction to non-streaming" silently drops it: a client asking for SSE receives (under F-2 rule 2) a buffered JSON array re-served as non-streamed JSON — a protocol downgrade the client did not ask for.
- **Recommendation:** Specify query handling for the streaming Gemini path: forward `alt=sse` when present (whitelist the `alt` parameter only — never `key`, preserving F-9) or unconditionally append `alt=sse` for the streaming method. Add a test asserting the upstream request carries `alt=sse`.

### F-4 — Medium — Test plan — wiremock cannot stream or drop mid-stream; hit-count assertions are sufficient only for the no-retry property
- **Category:** Testing adequacy vs docs/11 (challenge #6).
- **Evidence:** docs.rs wiremock 0.6.5: `ResponseTemplate` body setters are `set_body_bytes/json/string/raw` — all fully materialized; the `Respond` trait must return a `ResponseTemplate`, so there is **no streaming escape hatch**. Mid-stream upstream close, stalled streams, and drain-with-open-stream are therefore untestable with the plan's wiremock stack, and the plan lists no substitute. docs/11 mandates "streaming; no retry after stream commitment"; FR-017 requires streaming responses to "terminate cleanly" on drain. Single-upstream-hit assertions are sound structural evidence that rotation is impossible after commit (the loop is exited before body relay) — but they say nothing about what the *client* experiences when the upstream dies mid-stream, which is the user-visible half of the commitment story.
- **Recommendation:** Add a raw-`TcpListener` mock (hand-written HTTP/1.1 + chunked framing) or an in-test hyper server for four scenarios: (1) upstream closes mid-stream → client stream ends truncated, exactly one upstream hit, no rotation, no post-head 5xx; (2) a stream outliving `policy.timeout_ms` is relayed past it (F-1 regression guard); (3) FR-017 `stop(grace)` with an active SSE stream terminates within the grace (bounded); (4) FR-021 permit is released when the client disconnects mid-stream (a follow-up request to the concurrency-1 deployment then succeeds). Keep the hit-count assertions for the no-retry property; do not present them as evidence for termination semantics.

### F-5 — Medium — Records — FR-011 semantics for streamed rows are undefined (challenge #4)
- **Category:** Records honesty / traceability.
- **Evidence:** FR-011: "token usage **when supplied**." For streamed responses usage *is* supplied — mid-stream (OpenAI final usage chunk when the client sets `stream_options.include_usage`; Anthropic `message_start`/`message_delta` usage; Gemini trailing `usageMetadata`) — and v0 passthrough does not parse frames, so NULLs. Additionally the plan records streaming rows "at commit time", which makes `latency_ms` mean time-to-commit (≈TTFB), not request duration, and means a stream that later fails still records status 200.
- **Recommendation:** Deferral is defensible; silence is not. (a) Mark streamed rows (e.g. a `streamed: true` flag inside `decision_json`) so NULL tokens read as "not captured (streamed)" rather than a capture bug; (b) document that streamed-row latency is commit latency and status is commit-time truth; (c) record the residual in `docs/TRACEABILITY_MATRIX.md` against FR-010/FR-011 ("v0 streams are passthrough; usage-frame parsing deferred") — the honest FR-011 statement is "supplied upstream, not captured in v0"; (d) when usage parsing lands later, extract counters only — frame content must never enter records (ADR-008).

### F-6 — Low — Plan completeness items
- **Category:** Implementation notes (challenges #2, #5, #7).
- **Evidence/Recommendation:**
  - (a) The Phase-6 rejection points to remove/invert are not enumerated: `api.rs` `validate_request` (OpenAI and Anthropic `streaming_not_supported` arms), the Gemini `:streamGenerateContent` 400 branch, the adapter-level rejections in `openai.rs`/`anthropic.rs`/`gemini.rs`, and the tests `streaming_is_rejected_structurally` + `streaming_rejected_early`. List them so none survives into Phase 7.
  - (b) Pre-commit classification requires a full body read of error responses; bound it with `MAX_RESPONSE_BYTES` and say so (a hostile upstream can send an unbounded 4xx body — SECURITY_RULES #8).
  - (c) Header policy for streamed responses: Content-Type passthrough only — also forbid relaying upstream `content-length` (conflicts with chunked re-encoding) and never relay hop-by-hop or `set-cookie` headers.
  - (d) Unbounded relay: the 32 MiB response cap protects the non-streaming path; a streaming passthrough is inherently unbounded. Accept that explicitly for an authenticated loopback gateway and document the exception in the plan (SECURITY_RULES #8: validate payload sizes or document the exception; never silently drop the cap).
  - (e) Make the FR-021 wording normative: the permit moves **into** the body stream; `drop(deployment_permit)` at handler return (the non-streaming arm's habit) must not appear on the streaming path. Note for the record: the gateway-global `concurrency_guard` releases its slot at response head (pre-existing middleware behavior), so open streams are bounded by per-deployment semaphores only — document as known v0 semantics.
  - (f) QUALITY_GATES "Provider: … streaming where declared" — state the live-test status line (mock-based evidence only; opt-in live streaming tests deferred) as prior phase reviews required, so the gate is not silently unmet.

---

## Verdict

VERDICT: REVISE BEFORE IMPLEMENTATION — F-1 and F-2 are blocking (implementing as written produces streams killed at 120 s by the project's own timeout stack, and a commit predicate that cannot be implemented from headers as specified — both contradict docs/05 and ADR-017); F-3–F-5 must be folded into the same plan revision; F-6 items are implementation requirements, not optional. The core architecture is sound and externally verified: header-commit boundary, pre-commit-only rotation with ADR-017 semantics, permit-carrying stream for FR-021, axum `Body::from_stream`/reqwest `bytes_stream()` compatibility, and a gateway timeout layer confirmed (from the locked tower-http 0.6.11 source) not to interfere with streamed bodies. With F-1/F-2 resolved and the four raw-socket tests of F-4 added, the plan covers the docs/11 streaming scenarios honestly.
