## Findings

### F-11-1 — High — Clean-install checklist: "temp HOME override" cannot isolate the data dir on Windows and will silently run against the real user's data

- **Category:** Release-evidence validity (docs/12 clean-machine install).
- **Evidence:** The plan's §3 specifies "First-run behavior on a clean data dir (temp HOME override)". The DB directory comes from Tauri's `app_data_dir()` (`apps/desktop/src-tauri/src/lib.rs:112-116`), which on Windows resolves via `SHGetKnownFolderPath(FOLDERID_RoamingAppData)` — it does **not** consult the `HOME` (or `APPDATA`) environment variable, so a HOME override moves nothing on the primary dev/CI platform. Worse, the log directory is resolved by reading the `APPDATA` env var directly (`apps/desktop/src-tauri/src/telemetry.rs:113-115`), so an `APPDATA` override would relocate *logs only* while the DB stays in the real `%APPDATA%` — a split state in which the "clean first-run" migration test actually runs migrations against the developer's real `shahid.db` (false pass + real-data pollution). The override does work on macOS (`dirs` reads `$HOME` there), but macOS verification is itself owner-pending (ADR-016). Additionally, first-run mints a gateway token into the real OS vault — a dev-machine run is not a clean vault either.
- **Recommendation:** Pick one mechanism and write it into the plan: (a) run the clean-install verification under a fresh Windows user account / clean VM (true clean machine, also satisfies docs/12's "clean-machine install" wording); (b) run it on macOS with the HOME override (valid there, but folds into the existing ADR-016 owner dependency); or (c) add an app-level data-dir override env var (small code change, also useful for tests). Whichever is chosen, state that the temp-HOME mechanism is macOS/Linux-only, and account for the real OS-vault write during first-run.

### F-11-2 — High — Release scope vs docs/12: no platform bundle/installer is produced or verified, and update/upgrade behavior is unaddressed

- **Category:** Gate completeness vs docs/12 (PRD for this phase).
- **Evidence:** docs/12 requires "platform builds; clean-machine install; gateway lifecycle and credential vault verification; signing/notarization" and "verify … installer and update behavior", plus "test upgrades from previous release, preserve user data … provide recovery guidance". The plan reduces this to `cargo build --release` + `tauri build --no-bundle` + first-run smoke. Consequences: (1) **no installer artifact exists** — `--no-bundle` produces no MSI/NSIS/.app, so nothing about install, uninstall, or installer behavior is verifiable; (2) the plan conflates *signing* being owner-blocked with *bundling* being blocked — unsigned NSIS/MSI bundles build without certificates on Windows, and an unsigned macOS .app builds locally; (3) **update behavior is never mentioned** — v1 has no auto-updater (consistent with docs/06 "network requests only for … explicitly enabled update/diagnostic features"), and that absence is a release fact that must be stated in release notes/checklist, not left silent; (4) **upgrade-from-previous is never mentioned** — honest for v1 (no previous release exists) but it must be recorded as an explicit N/A with the compensating control named (schema-migration tests from every historical version, per planning-audit §6), so the release claim is complete; (5) the frontend dependency audit is missing — `cargo audit` covers Rust only; docs/12's "dependency/security audit" includes the npm tree in `apps/desktop/ui`.
- **Recommendation:** Amend §3: build the unsigned Windows bundle (NSIS) and install/launch/uninstall it on the clean environment from F-11-1, asserting user data survives uninstall (docs/12 requirement the plan already half-covers); record macOS bundle + signing/notarization as the owner-blocked residual. Add to the checklist: "update behavior: no auto-updater in v1 (manual update; data dir preserved)" and "upgrade-from-previous: N/A for v1, first release; schema-migration coverage is the data-preservation evidence". Add `npm audit` (or pnpm equivalent) to the audit step. Rename the §3 heading honestly: today it is a clean-*data-dir* checklist, not docs/12's clean-*machine* install, unless the F-11-1 fix makes it one.

### F-11-3 — Medium — The four raw-TCP scenarios are named but not specified; one required scenario from Phase 7 F-1 is missing, and "stream-outliving-timeout" is ambiguous about *which* timeout

- **Category:** Testing adequacy (docs/11; phase-7-review F-4 closure).
- **Evidence:** The plan lists scenario names only. Names are not assertions, and two ambiguities will bite during implementation:
  - **Scenario 2 ambiguity.** "Stream outliving timeout" conflates two different timeouts. Phase 7 F-1's resolution removed the per-attempt *total* deadline (`policy.timeout_ms`) from the streaming path but relies on a **hard-coded 300 s idle `read_timeout`** (`crates/sair-providers/src/http.rs:349`). F-1 therefore required *two* tests: (a) a stream relayed past `policy.timeout_ms` (total-deadline regression guard) and (b) a stalled stream cut by the idle timeout. Test (b) is **unimplementable as the code stands** (300 s wait) and is entirely absent from the plan — a stalled upstream holds the deployment permit and the connection for up to 300 s today, an untested operational bound.
  - **Scenario 3 (drain) semantics.** `stop(grace)` (`crates/sair-gateway/src/handle.rs:181-191`) breaks the accept loop, drops the listener, then joins connection tasks under a **hard-coded inner 30 s cap** (`handle.rs:147`) inside an outer `grace` that aborts the whole task on elapse (`DrainTimedOut`). Two behaviors must be pinned: streams *finish* inside grace (graceful path, Ok) and streams are *aborted bounded* when grace elapses (DrainTimedOut + client stream cut + port closed). Also note the >30 s edge: if grace exceeds the inner 30 s cap, the server task ends at 30 s, cutting still-open streams while `stop` returns **Ok** — success reported for an aborted drain. Impractical to test, but it must be documented (or the inner window set = grace).
- **Recommendation:** Write the assertions into the plan (implementable as stated against the current code):
  1. **Mid-stream drop** — two credentials in the pool, two raw listeners; upstream A sends `200` + SSE headers + 2 frames, then closes. Assert: client receives exactly the pre-drop frames then stream end (EOF/truncation, no post-head 5xx/408); upstream A hit once, upstream B hit **zero** times (this is what makes "no rotation" observable — a single-credential pool proves nothing); request record status 200 (commit-time truth), `streamed: true`, tokens NULL; gateway healthy afterwards (follow-up non-streaming request succeeds — guards permit/task leaks).
  2. **Stream outliving timeout** — test policy `timeout_ms` ≈ 500; upstream sends a frame every ~150 ms for ~2 s, clean terminal frame. Assert: ≥1 frame arrives after the 500 ms mark and the terminal frame is received (no total deadline; F-1 regression guard); exactly one upstream hit. **Split out 2b (stalled stream)**: either make the idle `read_timeout` a parameter of `build_streaming_client` (client-level in reqwest 0.13, so a builder argument; test value ~500 ms; assert the stalled stream is cut within idle + margin and a follow-up request to a concurrency-1 deployment succeeds) or record the 300 s stall bound explicitly in the traceability matrix and release notes as a residual.
  3. **Drain with open stream** — client opens SSE, reads first frame, then `stop(grace)`. Assert *both* paths: (a) upstream finishes within grace → `stop` returns Ok, client received **all** frames including terminal (extends the existing non-streaming `in_flight_request_completes_during_graceful_drain` to streams); (b) upstream would run 10 s, grace = 1 s → `stop` returns `DrainTimedOut` within grace + margin, client stream terminates bounded, new connections refused after stop. Document the inner-30 s-cap edge case.
  4. **Permit release on disconnect** — concurrency-1 deployment; upstream sends headers + 1 frame then **holds the connection open** (never finishes); client reads the frame, then drops the connection. Assert: a second request to the same deployment succeeds within a bounded window (e.g., < 5 s) — proving the permit was released by the body drop, not held until upstream EOF — and the mock saw exactly 2 upstream connections total. This is the test that would catch the `drop(deployment_permit)`-at-handler-return habit phase-7-review F-6(e) warned about.

### F-11-4 — Medium — Perf methodology: metric not defined as a delta, 200 iterations make p99 statistically meaningless, and the vault-retrieval confounder is uncontrolled

- **Category:** Performance measurement design (planning-audit §6 budget).
- **Evidence:** The plan says "loopback relay latency (gateway → mock upstream) vs direct client→mock, 200 iterations, report p50/p95/p99; budget check p99 < 25 ms". Issues: (1) the budget is defined as **added latency** — the metric must be a delta (paired A/B), not an absolute p99 compared to 25 ms; the plan's wording permits the wrong reading. It also never states **non-streaming** requests, which is what the budget covers. (2) With 200 samples, p99 is the 2nd-worst sample — pure noise on any workstation. (3) No warmup, no interleaving: sequential A-then-B legs bias whichever leg absorbs machine drift. (4) Runtime flavor unstated — `#[tokio::test]` defaults to a single-threaded runtime where gateway and client share one thread; that is a legitimate, stable configuration but must be recorded, or use `multi_thread` for representativeness. (5) **Vault confounder:** the gateway retrieves the credential from the vault on every attempt (`api.rs:807`, per docs/06 "at call time only") — a real production cost that the test harness's (necessarily fake) vault does not exhibit. The measured delta therefore *understates* production gateway overhead by the OS-keychain read. (6) Mock choice: wiremock is acceptable **only** if the same mock serves both legs (its per-request overhead is then common-mode and cancels in the delta); a raw-TCP mock is preferable for determinism. Loopback HTTP with no TLS on either leg is correct and must be stated (TLS absence is part of the design being measured, not a confounder to remove).
- **Recommendation:** Specify in the plan: non-streaming requests; fixed small body (e.g., 1 KiB); paired/interleaved A-B iterations with 100+ warmup discarded; ≥1000 measured iterations (loopback round-trips are ~1 ms — cost is seconds), repeated 3× with the median p99-of-deltas reported; same mock for both legs (raw-TCP preferred); runtime flavor and machine state recorded (AC power, test run isolated from other tests); the fake-vault caveat stated, with one supplementary measurement of the real OS-vault retrieve cost documented separately; raw numbers archived under `reports/`. Keep the budget advisory: a local exceedance triggers investigation (suspects: per-request DNS in the validating resolver, sync keychain, accidental TLS), not an automatic release block.

### F-11-5 — Medium — Acceptance overclaims: "SBOM … archived" is not what the design produces, and the clean-install item inherits the F-11-1 flaw

- **Category:** Claim honesty (docs/11: "Do not claim bug-free software" spirit; docs/12 "SBOM where practical").
- **Evidence:** Design §4 honestly says SBOM via `cargo tree` JSON because "CycloneDX needs extra tooling", but the Acceptance line then claims "SBOM/checksums archived". A `cargo tree` dump is a dependency *inventory*: it lacks per-package checksums, licenses, and pURLs, and does not meet any SBOM standard. Meanwhile `cargo-cyclonedx` (or `cargo auditable`) is a one-command install — under docs/12's "where practical" it is hard to argue full tooling is impractical at the *final* phase. The overclaim would propagate into release notes if the acceptance wording is copied.
- **Recommendation:** Either (a) run `cargo cyclonedx` and archive real CycloneDX JSON (preferred — trivial cost at the release gate), or (b) keep the tree-based inventory but relabel it consistently — "dependency inventory (not a standards-compliant SBOM; full SBOM tooling post-v1)" — in the plan's acceptance line, the phase report, and the release notes, and supplement with `Cargo.lock` (which does carry source checksums). No other acceptance line overclaims: "no open Critical/High", checksums, and the BLOCKED signing note are all consistent with the design sections.

### F-11-6 — Medium — Final-gate definition is incomplete: FR-023's stale row, unnamed residuals, and owner-waiver discipline are not addressed

- **Category:** Release-claim honesty (docs/13 gate; docs/11 DoD and waiver rule).
- **Evidence:** The plan's acceptance says "traceability finalized (all FRs to final states with residuals)" but does not dispose of the specific open items, and one of them is currently **wrong in the matrix**: FR-023 ("Routing scope: v1 same-protocol only; Anthropic surface includes `/v1/messages/count_tokens`") is marked "Planned / TBD", yet the route is implemented (`crates/sair-gateway/src/api.rs:109`, handler at `api.rs:366`) and same-protocol routing shipped with Phase 5 — the row is stale and must be finalized with evidence, not silently left "Planned" under an "all FRs finalized" claim. Further, docs/06's threat-model addendum commits to revalidating its two residual risks (SSRF resolve-to-connect race; inbound DNS-rebinding) **at Phase 11** — the plan's security review mentions refreshing the addendum but not these two named revalidations. Finally, docs/11 states "Only an authorized human may approve a waiver; an agent cannot waive its own failed gate" — the plan's remaining gaps (signing/notarization, CI execution B-01, macOS runtime verification ADR-016) are exactly such waivers and must be routed to the owner, not absorbed into the agent-authored release claim.
- **Recommendation:** Define the final gate as an evidence bundle, and write it into the plan: (1) full local gate run (fmt, clippy `-D warnings`, `cargo test --workspace`, npm typecheck/test/build) with counts; (2) the four raw-TCP scenarios green and the FR-010 "raw-TCP Phase 11" residual closed in the matrix; (3) perf evidence per F-11-4; (4) independent security-review report (full diff since Phase 2) with verdict "no open Critical/High", cargo audit output archived, and the two addendum residual risks explicitly revalidated; (5) release checklist per F-11-1/F-11-2 including the update-behavior and upgrade-N/A statements; (6) inventory/SBOM + SHA-256 checksums + CHANGELOG + release notes; (7) traceability finalized with **FR-023 corrected** and every residual enumerated with an owner: streamed usage capture (FR-010/011), vision heuristic (FR-007), lru/pin 501 (FR-004), live CLI verification (FR-013), macOS restore CI evidence (FR-014/B-01), signing/notarization, CI execution, macOS runtime. The release claim itself must be worded "v1 code-complete with residuals; release artifacts unsigned pending owner waiver" — and "v1 released" may only be declared once the authorized human has signed the waiver list.

## Verdict

The plan selects the right work: the deferred F-4 scenario set is correct and raw-TCP is the right vehicle; the advisory budget treatment and the BLOCKED-signing honesty are right; the security-review scope is appropriate. But as drafted it would generate false or incomplete release evidence: the clean-install step does not work on Windows and risks touching real user data (F-11-1), the plan silently drops docs/12's platform-build/installer/update/upgrade requirements (F-11-2), the scenarios it exists to close are unspecified with one required scenario missing (F-11-3), the perf metric is ambiguous and statistically fragile with an uncontrolled vault confounder (F-11-4), the acceptance line overclaims SBOM (F-11-5), and the final-gate definition leaves FR-023 stale, addendum revalidations unnamed, and owner waivers un-routed (F-11-6).

VERDICT: REVISE BEFORE IMPLEMENTATION — F-11-1 and F-11-2 are blocking plan revisions (the clean-install mechanism as specified produces false evidence; docs/12's installer/update/upgrade scope is dropped); F-11-3 and F-11-4 must be folded into the same revision as concrete assertions and methodology; F-11-5 and F-11-6 are wording/evidence-discipline fixes that gate the final release claim, not the implementation. No architectural rework is needed — this is a bounded plan revision, after which the phase is executable and the "v1-complete-with-residuals" claim can be made honestly.
