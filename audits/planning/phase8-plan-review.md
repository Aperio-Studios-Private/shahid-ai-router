## Verified positives (checked, no finding)

- **Claude Code mechanism is current and correct.** The `env` block in `~/.claude/settings.json` is the documented settings mechanism; `ANTHROPIC_BASE_URL` ("Override the API endpoint to route requests through a proxy or gateway"), `ANTHROPIC_AUTH_TOKEN` ("Custom value for the `Authorization` header … prefixed with `Bearer `") and `ANTHROPIC_MODEL` are all documented env vars. `ANTHROPIC_AUTH_TOKEN`'s Bearer form matches the gateway's `Authorization: Bearer` extraction (lib.rs `extract_token`), and the plan's base URL (root, no `/v1`) is right — the client appends `/v1/messages`. `count_tokens` is proxied (api.rs:109), matching the plan's note.
- **Gemini CLI does accept a custom base URL, and loopback HTTP is explicitly allowed.** `GOOGLE_GEMINI_BASE_URL` overrides the Gemini API base URL "when using `gemini-api-key` authentication" and "must use HTTPS unless pointing to `localhost` (or `127.0.0.1` / `[::1]`)" — the plan's `http://127.0.0.1:{port}` is inside the documented exception.
- **Gemini key transmission is header-form, so the F-9 `?key=` rejection is moot for the CLI.** gemini-cli authenticates with `GEMINI_API_KEY` through `@google/genai`, which sets `x-goog-api-key` as a header (`src/cross/_cross_auth.ts:236`) — a form the gateway already accepts. The plan's "CLI must use the header form" premise holds; only the limitation's framing is off (F-4).
- **Generator placeholder policy matches the codebase's one-way-secret convention.** Generators take a token REFERENCE and emit `<<GATEWAY_TOKEN>>`; views never include secret material (commands_management.rs header comment); the reveal path already exists and is sweep-tested (Phase-2 addendum). No token enters `generate_agent_profile` output by design.
- **Gateway surface paths assumed by the generators exist as planned:** `/v1/chat/completions`, `/v1/messages`, `/v1/messages/count_tokens`, `/v1beta/models/{model_and_method}` (api.rs:105-113), all behind auth + Host allowlist.
- **`agent_profiles` schema already carries the docs/09 fields** (agent id/version, protocol family, endpoint, auth method, alias + fast alias FK, env_json, config_rules_json, verified_at, notes — 0001_init.sql:109-125), so the profile model needs no migration.
- **The plan honestly states what its E2E cannot do** ("the real CLIs cannot run in CI without installs … live CLI verification remains opt-in/manual, recorded as limitation") — the right posture per docs/09; what remains is to make the UI wording and `verified_at` semantics follow through (F-5).

## Findings

### F-1 — High — The Codex CLI generator emits a config format the current Codex CLI refuses to load; Codex cannot be a supported v1 agent
- Category: Factual staleness / spec fidelity (docs/09 "verify current official docs and actual versions"; SECURITY_RULES #11) / ADR-010 premise.
- Evidence: The plan's Codex generator pins `wire_api = "chat"` "(verified format 2026-10)". Re-verified 2026-10-31 against the current official Codex config reference and the `openai/codex` source: `WireApi` now has a single variant `Responses` (`codex-rs/model-provider-info/src/lib.rs:116-122`), and deserializing `"chat"` is a hard config-load error — `CHAT_WIRE_API_REMOVED_ERROR: "`wire_api = \"chat\"` is no longer supported. How to fix: set `wire_api = \"responses\"` …"` (lib.rs:109, 139). The current config reference states `wire_api` "responses is the only supported value, and it is the default when omitted". Chat support was deprecated Dec 2025 and removed early Feb 2026 (openai/codex discussion #7782). Meanwhile `/v1/responses` is out of scope v1 (FR-023, ADR-010), and `wire_api = "responses"` makes Codex call `{base_url}/responses` — a 404 on our gateway. Both branches fail: the generated profile cannot work against the documented current version.
- Consequence if implemented as written: users copy a config that errors at Codex startup, the profile ships with `verified_at` claiming 2026-10 verification of a format that was already dead at that date, and the E2E ("Codex-style TOML parsed … by a generic OpenAI client") is structurally incapable of catching it — a generic TOML parse proves nothing about Codex's enum. This is exactly the drift docs/09 warns about.
- Recommendation: drop the Codex generator from v1. Ship Codex as a documented **unsupported** entry in the Agent Integrations screen (limitations: "requires a `/v1/responses` surface, out of scope v1; `wire_api=\"chat\"` removed from Codex CLI ~Feb 2026 — see codex discussion #7782"), with no Apply flow for it. Amend ADR-010's Phase-8 parenthetical ("verified Phase 8" → removed-format finding, revisit trigger = implementing `/v1/responses`). If a pin-to-old-version escape hatch is ever considered, it must be a documented downgrade with the version recorded in `agent_version` — not a v1 generator.

### F-2 — High — `apply_agent_profile` as specified is an arbitrary-file-write primitive; the "allowlist" is not an allowlist and consent lives only in the webview
- Category: Security (docs/06 "narrow validated commands", "Import: strict size/file/path/schema limits"; QUALITY_GATES "Security-sensitive changes").
- Evidence: Plan §3: apply "refuses paths outside a small allowlist (the four known config paths **+ explicit user-provided path** with absolute normalization)". The user-provided exception collapses the allowlist: the command accepts (path, content) with `content` supplied by the webview, so any compromised or buggy webview code (the trust boundary Tauri commands defend against) gains a persistent arbitrary-write — shell rc, VS Code/cron/auto-start entries, SSH config — with attacker-chosen content. The listed mitigations (size cap, no-symlink, normalization) do not restore a path allowlist. Consent ("the UI shows a diff/backup prompt") is enforced in the frontend layer, which is the compromised component in this threat model; the backend `consent-less call rejected` test implies a consent flag, but a flag passed from the webview is webview-controlled input. docs/06 lists "unsafe agent integrations" in the threat model and QUALITY_GATES requires a threat-model update for security-sensitive changes — the plan has no addendum entry for the new external-file-write surface.
- Recommendation: (a) make the allowlist closed — the four known config paths resolved from the OS home directory; if a custom path is genuinely required, it must be selected through an OS-native file dialog (user gesture outside the webview), then canonicalized and re-validated backend-side; (b) enforce consent in the backend as a two-step flow (prepare → returns id + diff + backup plan; confirm(id, expected_hash) → apply), with the hash precondition closing the shown-diff/apply TOCTOU gap (file changed between prompt and write); (c) symlink policy must cover parent components and Windows realities (junctions, ADS `file.toml:stream`, device paths `\\?\`/`\\.\`) — "never follows symlinks" needs a mechanism (canonicalize parent + final-component check or open-with-no-follow), not an intention; (d) write via temp-file + atomic rename with backup created first; define `.shahid-backup-<ts>` collision behavior; (e) add a docs/06 threat-model addendum entry for local config-file writes and the negative tests above.

### F-3 — Medium — Token flows through apply/backup are under-specified: the placeholder policy is intended, not enforced, and backups accumulate plaintext token copies
- Category: Secrets (docs/06 "Never log … export plaintext"; docs/06 addendum pattern).
- Evidence: The placeholder rule binds the generators, but `apply_agent_profile(path, content)` takes content from the UI, and the plan explicitly contemplates the UI substituting the real token "on reveal" — so the real token can transit IPC and be written to the destination file and to `<path>.shahid-backup-<ts>` in plaintext. That is inherent to FR-013 (the agent must receive the token) but the plan nowhere: states that apply content is never logged (the Phase-2 log-redaction sweep's "any sink" scope must be extended to the apply/backup paths), warns the user in the consent dialog that the destination file and its backups will contain the token in plaintext (docs/06 "Mask in UI" / Secrets tension, resolved as explicit consented export), or defines backup retention — after FR-019 token regeneration, old backups still contain the retired token indefinitely. The plan's own test list ("no token material in output (sweep)") covers generator output only, i.e. the placeholder is enforced where the token never flows and unenforced where it does.
- Recommendation: one paragraph + tests: apply/backup content never enters spans/logs (sweep test seeded with a fake token through the full apply→backup path); consent dialog states the plaintext-at-rest fact and points at rollback/regeneration; define backup retention (e.g. keep N, prune M days) or state why indefinite is accepted; regenerate-flow note that backups retain prior tokens.

### F-4 — Medium — Gemini generator: the `/v1beta` suffix does not belong in the base URL, and the config-file story is wrong (settings.json has no base-URL field)
- Category: Generator correctness (docs/09 "config file rules"; "Do not assume all agents accept custom base URLs or share environment variables").
- Evidence: (a) The base URL override is the env var `GOOGLE_GEMINI_BASE_URL`, consumed by `@google/genai`, which builds request URLs as `{baseUrl}/{apiVersion}/…` with default apiVersion `v1beta` (`src/_api_client.ts:448-452`, `GOOGLE_AI_API_DEFAULT_VERSION`) — so the value must be the bare `http://127.0.0.1:{port}`; the plan's `http://127.0.0.1:{port}/v1beta` would produce `/v1beta/v1beta/models/…` and 404 on every request. (b) The plan's "files it would touch" names `~/.gemini/settings.json` for endpoint config, but settings.json has no base-URL field — endpoint, key and model are environment variables (`GOOGLE_GEMINI_BASE_URL`, `GEMINI_API_KEY`, `GEMINI_MODEL`), settable in the shell profile or `~/.gemini/.env` (which the CLI loads; `.gemini/.env` variables are never excluded per the configuration reference). The apply flow for Gemini therefore targets different files than the plan names. (c) The recorded limitation ("query-param auth rejected by the gateway — the CLI must use the header form") frames a risk that does not exist for this client (it sends `x-goog-api-key`, verified above); the real limitations are: base-URL override applies only with `gemini-api-key` auth mode, and only the `generateContent`/`streamGenerateContent` surface is served (CLI features hitting other endpoints get 404).
- Recommendation: fix the generator spec — bare base URL into `GOOGLE_GEMINI_BASE_URL`, model via `GEMINI_MODEL` (or settings.json `model`), key via `GEMINI_API_KEY` in `~/.gemini/.env`/shell profile; correct the files-touched list; replace the `?key=` limitation with the auth-mode and surface-coverage limitations. Add a unit test pinning the produced env values (bare base URL, exact var names) against a dated-citation fixture, since the plan's own E2E ("Gemini header form used by the Gemini adapter path") tests the gateway, not the CLI's URL construction.

### F-5 — Medium — Verification story: `verified_at` and UI wording must not imply "supported"; alias validation and dated format citations are missing
- Category: Honesty (docs/09 "Support is not complete until end-to-end tested on the documented version"; SECURITY_RULES #11; QUALITY_GATES "state exactly what was tested").
- Evidence: The plan's E2E tests our gateway with generic clients — that is "config parses + gateway serves the documented contract", and the plan says so. But §3 then says profiles "ship with `verified_at` = this phase's E2E evidence", and nothing forbids the UI from presenting the agent as supported. F-1 is the existence proof that this verification class cannot detect client-side format rejection. Additionally: `generate_agent_profile(agent_id, alias, port)` never validates the alias (exists, has ≥1 enabled deployment whose `protocol_family` matches the agent's family) — generating a Claude Code profile for an openai-only alias produces a config that fails at first request with NoEligibleDeployment; and nothing states which agent/doc version populates `agent_version`.
- Recommendation: (a) UI wording fixed by spec: "contract-tested", never "supported"; each profile shows limitations text verbatim; `verified_at` = date of contract evidence with an explicit "live CLI not verified" marker per docs/09; (b) generator validates alias/family before producing output (structured error otherwise) and records the doc-verified agent version in `agent_version`; (c) each generator carries a dated citation comment (docs URL + access date) and a fixture test — F-1/F-4 show the fixtures drift silently; (d) state the opt-in live-test deferral explicitly in the phase report per the Phase-5/6 precedent (QUALITY_GATES "Provider: … opt-in live test").

### F-6 — Low — Minor gaps: Claude Code fast-alias variable, Windows path handling, limitations storage
- Category: Completeness.
- Evidence: (a) docs/09 profiles carry an "optional fast model alias"; the plan's Claude Code env block has no mapping for it, and `ANTHROPIC_SMALL_FAST_MODEL` is documented as deprecated — the current mechanism is `ANTHROPIC_DEFAULT_HAIKU_MODEL`. (b) The allowlisted paths are `~/.codex/config.toml`, `~/.claude/settings.json`, `~/.gemini/settings.json` — on Windows these resolve via `%USERPROFILE%`; the plan should require home-dir-relative resolution and rejection of UNC/device paths (overlaps F-2(c)). (c) docs/09 requires each profile to record "limitations"; `agent_profiles` has no limitations column — the plan should say limitations are stored in `notes` (and `config_rules_json` for file rules) so it is not read as a schema change.
- Recommendation: map fast alias → `ANTHROPIC_DEFAULT_HAIKU_MODEL` or omit the field for v1; state the `notes` mapping explicitly.

## Verdict

VERDICT: APPROVED WITH REQUIRED REVISIONS — F-1 and F-2 are blocking and must be incorporated before implementation begins (F-1: the Codex generator emits a config the current Codex CLI hard-rejects and no v1 fallback exists — ship Codex as documented-unsupported and amend ADR-010; F-2: close the file-write allowlist and enforce consent/validation backend-side with a threat-model addendum). F-3–F-5 should be folded into the same plan revision (token/backup handling, Gemini base-URL and file-target corrections, verified_at/UI-wording honesty). F-6 is a recommendation. The plan's core shape is sound and the non-Codex generators are externally verified against current docs: Claude Code's settings.json env mechanism and Bearer-form auth match the gateway, Gemini CLI's custom base URL exists with an explicit loopback-HTTP exception and header-form key transmission, and the placeholder-first generator design matches the codebase's one-way-secret conventions.
